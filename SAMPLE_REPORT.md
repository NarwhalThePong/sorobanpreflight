## Checklist

### Storage TTL / archival

- [ ] **ST-02** Value-bearing data kept in temporary storage — _high review priority_ — 1 hit(s)
  - Why it matters: Temporary entries are deleted for good when their TTL expires and cannot be restored. Balances, allowances that must persist, ownership or admin keys in temporary storage can silently vanish.
  - How to verify: Use persistent storage for balances, positions and ownership, and instance storage for contract-wide config. Keep temporary storage for data that is fine to lose (nonces with expiry, short-lived allowances with an explicit expiration ledger).
  - `src/lib.rs:40` — temporary storage key DataKey::Balance(user)
- [ ] **ST-01** Persistent or instance entry written with no TTL extension in the same function — _medium review priority_ — 4 hit(s)
  - Why it matters: Persistent and instance entries are archived when their TTL runs out. A contract that writes balances, config or the admin key but never calls extend_ttl relies on users or ops to bump TTL, or on restore, and an archived instance makes the whole contract unusable until restored.
  - How to verify: Call env.storage().persistent().extend_ttl(&key, threshold, extend_to) after writing long-lived keys, and env.storage().instance().extend_ttl(threshold, extend_to) in entry points. If TTL is bumped by a helper or an off-chain job, document it.
  - `src/lib.rs:15` — initialize() writes persistent/instance storage without extend_ttl
  - `src/lib.rs:25` — deposit() writes persistent/instance storage without extend_ttl
  - `src/lib.rs:33` — withdraw() writes persistent/instance storage without extend_ttl
  - `src/lib.rs:48` — join() writes persistent/instance storage without extend_ttl
- [ ] **ST-03** Per-user data keyed into instance storage — _medium review priority_ — 2 hit(s)
  - Why it matters: Instance storage is one ledger entry shared with the contract instance: it is loaded on every call and its total size is capped by the ledger entry size limit. Per-user balances, allowances or positions there grow without bound until every call to the contract fails.
  - How to verify: Keep per-user or per-id data in persistent storage (env.storage().persistent()) under one key per user; keep instance storage for small, bounded, contract-wide config such as the admin or token pair.
  - `src/lib.rs:80` — instance storage key DataKey::Balance(from)
  - `src/lib.rs:81` — instance storage key DataKey::Balance(to)

### Resource budgets

- [ ] **RB-01** Loop over a caller-supplied Vec/Map with no length bound — _medium review priority_ — 1 hit(s)
  - Why it matters: Soroban transactions have hard CPU, memory and read/write limits. A loop over an unbounded caller-supplied collection can exceed the budget and fail, and a loop over a stored collection that anyone can grow can lock a function forever.
  - How to verify: Check the length against a constant (if v.len() > MAX { panic_with_error!(...) }) before the loop, or paginate. Measure the worst case with the test budget (env.cost_estimate().budget()).
  - `src/lib.rs:54` — total_of() loops over parameter users with no len() bound
- [ ] **RB-03** Stored Vec/Map grown by push/insert with no size cap — _medium review priority_ — 1 hit(s)
  - Why it matters: An entry that any caller can append to keeps growing. Once it is too big to read within the entry size or budget limits, every function that loads it fails, which is a permanent denial of service.
  - How to verify: Cap the collection length, or store one entry per item (a key per user or per id) instead of one growing Vec/Map.
  - `src/lib.rs:47` — join() grows a collection and writes it to storage with no length check
- [ ] **RB-02** Storage read or write inside a loop — _low review priority_ — 1 hit(s)
  - Why it matters: Each ledger entry access counts toward the per-transaction read/write entry and byte limits. Storage access in a loop grows with input size and is a common cause of budget-exceeded failures.
  - How to verify: Bound the loop, batch the data into one entry, or read once before the loop. Confirm the worst case fits the network limits in a test.
  - `src/lib.rs:55` — storage access inside a loop in total_of()

### Authorization

- [ ] **AU-01** Entry point changes state with no require_auth — _high review priority_ — 1 hit(s)
  - Why it matters: Soroban has no implicit msg.sender. If a function that moves value or writes state never calls require_auth / require_auth_for_args on the acting Address, anyone can call it on behalf of anyone.
  - How to verify: Call addr.require_auth() (or require_auth_for_args) on the address whose funds or rights are used, before any state change. If the function is intentionally open (permissionless keeper), note it in scope docs.
  - `src/lib.rs:29` — withdraw() writes state or calls a token with no require_auth
- [ ] **AU-02** Privileged function authorizes a caller-supplied address, not the stored admin — _high review priority_ — 1 hit(s)
  - Why it matters: admin.require_auth() only proves that the given address signed. If admin is a function parameter rather than the address loaded from storage, any account can pass itself and pass the check.
  - How to verify: Load the admin from storage (let admin: Address = env.storage().instance().get(&DataKey::Admin).unwrap();) and call require_auth on that value.
  - `src/lib.rs:62` — set_token() calls require_auth only on a parameter address
- [ ] **AU-03** Token-style function authorizes the wrong address — _high review priority_ — 1 hit(s)
  - Why it matters: In the SEP-41 token interface, transfer, burn and approve must be authorized by `from`, and transfer_from / burn_from by `spender` (whose allowance is then consumed). Authorizing some other address (for example `to`, or `from` in transfer_from without an allowance check) lets one account move another account's balance.
  - How to verify: Call from.require_auth() in transfer, burn and approve; call spender.require_auth() and spend the allowance in transfer_from and burn_from. See the token interface on developers.stellar.org.
  - `src/lib.rs:75` — transfer() calls require_auth on to but not on from

### Arithmetic

- [ ] **AR-01** Unchecked +, -, * on i128/u128/i64/u64 amounts — _medium review priority_ — 2 hit(s)
  - Why it matters: Plain arithmetic wraps silently in release builds unless overflow-checks = true is set in the Cargo release profile. Negative i128 amounts are also valid inputs and can flip a subtraction into an addition.
  - How to verify: Use checked_add / checked_sub / checked_mul (returning an error), or set overflow-checks = true in [profile.release] and check it in CI. Reject amount < 0 (or <= 0) at entry.
  - `src/lib.rs:25` — unchecked arithmetic in deposit()
  - `src/lib.rs:33` — unchecked arithmetic in withdraw()
- [ ] **AR-03** Signed amount parameter used without a sign check — _medium review priority_ — 1 hit(s)
  - Why it matters: Token amounts are i128 in the Soroban token interface. A negative amount passed to deposit/withdraw/transfer logic can reverse the direction of balance changes.
  - How to verify: Reject amount < 0 (or <= 0) at the top of every function that takes an i128 amount.
  - `src/lib.rs:29` — withdraw(amount: i128) has no sign check
- [ ] **AR-02** Narrowing or sign-changing `as` cast on a numeric value — _low review priority_ — 1 hit(s)
  - Why it matters: `as` truncates or reinterprets silently (i128 as u64, u128 as i128, i128 as u32). A large or negative amount becomes a different, valid-looking number.
  - How to verify: Use try_from / try_into and return an error on failure.
  - `src/lib.rs:71` — cast to u32

### Init / upgrade

- [ ] **IN-01** initialize can be called more than once — _high review priority_ — 1 hit(s)
  - Why it matters: A public init function with no already-initialized guard lets anyone call it again and replace the admin or token config. Unlike __constructor (protocol 22+), a normal init function is callable at any time.
  - How to verify: Panic if the admin/config key already exists (if env.storage().instance().has(&DataKey::Admin) { panic_with_error!(...) }), or move setup into __constructor so it runs exactly once at deploy.
  - `src/lib.rs:14` — initialize() writes storage with no already-initialized check
- [ ] **IN-02** Contract Wasm upgrade with no admin authorization — _high review priority_ — 1 hit(s)
  - Why it matters: update_current_contract_wasm replaces the contract code. If the function that calls it does not require the stored admin to authorize, anyone can swap in arbitrary code and take every asset.
  - How to verify: Load the stored admin and call admin.require_auth() before env.deployer().update_current_contract_wasm(hash). Consider a timelock or multisig admin.
  - `src/lib.rs:70` — upgrade() upgrades the Wasm with no require_auth

### Cross-contract calls

- [ ] **RE-02** Token or contract address taken from the caller — _high review priority_ — 1 hit(s)
  - Why it matters: A function that builds a token client from an Address parameter will call whatever contract the caller names. A fake token can report success without moving value, so deposits can be credited for nothing and later paid out in the real token.
  - How to verify: Load token addresses from storage set by the admin, or check the parameter against an allow-list.
  - `src/lib.rs:23` — deposit() builds TokenClient from parameter token_addr
- [ ] **RE-01** State written after an external token or contract call — _low review priority_ — 2 hit(s)
  - Why it matters: Soroban blocks direct re-entry into the same contract, but the called token or contract can be malicious or call other contracts that read your stale state, and a failed/unexpected callee leaves accounting half-updated. Updating state first (checks-effects-interactions) keeps the contract consistent.
  - How to verify: Move storage writes before the token transfer / invoke_contract call, or document why the order is safe. Only call token contracts you trust or have allow-listed.
  - `src/lib.rs:25` — deposit() writes storage after an external call
  - `src/lib.rs:33` — withdraw() writes storage after an external call
